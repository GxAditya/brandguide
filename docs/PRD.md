# PRD — BrandKit: Live Brand Extraction API

> Give it a company name or URL. Get back a usable brand guide — logo, colour
> palette, typography, tone of voice, key messaging — pulled from the live site.

- **Bounty:** TinyFish "Brand Guide Generator"
- **Status:** Built. This document is the original plan, kept for reference.
- **Owner:** aditya

> **Where the build diverged from this plan.** Two of the four endpoints in §4 were
> never wired up: `POST /api/v1/identity` and `POST /api/v1/voice` are not in
> `src/server/index.js` and return `404`. `GET /api/v1/schema` likewise does not
> exist; the schema is exported from `src/schema.js`. The extraction those endpoints
> described is real and runs inside the brand-guide and compare pipelines, and its
> output is in the guide and the `?format=` exports. Two sections also drifted from
> the code and are marked in place. **The README is the current source of truth for
> what exists.** `TASKS.md` records what actually shipped.

---

## 1. Problem

Marketing teams and AI-CMO-style products need a machine-readable brand kit for
any company, and today getting one means either paying an agency, asking a
designer, or pasting screenshots into a chat window. Existing "brand colour
scrapers" grab one hex value from the homepage and call it a day. The useful
product is not a screenshot — it is a **structured, evidence-backed object** a
marketer can paste into a deck or push into Figma, Tailwind, or a brand
service.

## 2. What we are building

A zero-dependency Node service plus a single-page web UI that turns a **URL or
company name** into a **structured brand guide**, extracted from the live site.

The output is not prose. It is a versioned JSON object with a published JSON
Schema, plus renderings as Markdown, CSS custom properties, Tailwind theme,
Style Dictionary JSON, and Figma Variables.

### Non-goals

- Not a logo re-generation tool. We return **verified live asset URLs**, not redrawn marks.
- Not a CMS. Generated guides are ephemeral; persistence is explicitly out of scope.
- Not an LLM wrapper. Hard facts (colour, type, logo) are extracted deterministically from fetched markup and CSS and are **never** generated by a model.

---

## 3. Key architectural decision: TinyFish is the entire read layer

The whole product reads the live web through TinyFish and nothing else. There is
no direct `fetch()` of the target site, no headless browser in the default path,
and no scraping library.

This was validated with a spike against `linear.app` before writing this PRD:

| Need | TinyFish surface used | Result |
| --- | --- | --- |
| Resolve `"Vercel"` → a domain | `Search` | ranked results, pick official site |
| `og:image`, `og:title`, `theme-color`, `<link rel=icon>`, manifest, **all 49 stylesheet URLs** | `Fetch` with `include_selectors: ["head"]`, `format: "html"` | returns the `<head>` **verbatim**; styles/scripts stripped but every `<link>` and `<meta>` survives |
| Actual colours, `@font-face`, CSS custom properties | `Fetch` on each stylesheet URL | returns **raw CSS as text** |
| Page copy, headings, nav structure, outbound links, images | `Fetch` with `format: "html"`, `links: true`, `image_links: true` | cleaned semantic HTML + absolute URLs |
| Voice / messaging corpus | `Fetch` on `/about`, `/careers`, `/blog`, `/press`, `/pricing` | real sentences to analyse |
| Does that logo URL actually exist? | `Fetch` on the candidate | `empty_content` on a 404 ⇒ candidate rejected |
| Benchmark competitors | `Search`, then `Fetch` each | comparable vectors |

`Fetch` renders in a real browser and handles JS-heavy sites, so this works for
SPAs (`linear.app` is a Next.js app and reads fine) as well as static sites.

Search and Fetch are free at any balance, so the default path costs nothing.

### On the LLM question

TinyFish has four surfaces — Search, Fetch, Browser, Agent — and **none of them
is a language model**. Agent automates a browser; it does not write prose. So
extraction and interpretation are separated:

- **Deterministic core (always on, no model).** Colours, contrast math, type
  families, weights, logo verification, token graphs, and a lexical voice
  profile are computed from fetched bytes. Reproducible, auditable, free.
- **Optional interpretation layer (a Gemini key, or any OpenAI-compatible
  endpoint, supplied by the caller).** Upgrades *narrative* only: the tone paragraph,
  message pillars, positioning line, do/don't guidance. Every LLM sentence is
  required to carry a `sourceUrl`. The model is structurally unable to touch
  colour, type, or logo fields — they are attached after generation.

The app is fully functional with no LLM key. That is the default.

## 4. Endpoints

> **As built: two.** `POST /api/v1/brand-guide` (also over `GET`) and
> `POST /api/v1/compare`. The plan below lists four; §4.2 and §4.3 were folded into
> §4.1 rather than shipped as separate routes, and §4.4 shipped as planned. The
> capability each described is still present in the output.

### 4.1 `POST /api/v1/brand-guide` — the kit

`{ input, depth?, pages? }` → complete brand guide. `pages` (4-24) is the guide
length budget; see §7.1.

Pipeline: `Search` (if input is a name) → `Fetch` head → `Fetch` stylesheets →
`Fetch` 4–8 content pages → compose.

```jsonc
{
  "schemaVersion": "1.0.0",
  "input": { "given": "linear", "resolvedUrl": "https://linear.app", "resolvedBy": "search|direct" },
  "identity": { "name", "legalName", "tagline", "description", "industry", "founded" },
  "logos":      { "primary": {...}, "alternates": [...], "markOnly": {...} },
  "colors":     { "tokens": [...], "roles": {...} },
  "typography": { "families": [...], "scale": [...], "pairing": {...} },
  "voice":      { "vector": {...}, "summary", "do": [], "dont": [] },
  "messaging":  { "pillars": [...], "taglineCandidates": [], "boilerplate": [] },
  "confidence": { "overall": 0.0, "bySection": {} },
  "provenance": { "calls": [...], "pages": [...] },
  "deck":       { "requestedPages": 14 },
  "warnings":   []
}
```

### 4.2 `POST /api/v1/identity` — visual forensics *(never shipped as a route)*

`{ url }` → design-token payload. Goes **deeper into CSS** than the kit:
resolves `--var` alias chains to final values, walks the token graph, assigns
semantic roles from token *names* (`--color-bg-primary`, `--brand-500`), builds
WCAG contrast matrices over real foreground/background pairs, derives the type
scale from `clamp()`/`rem` rules, and verifies every asset through `Fetch`
with format + byte-size detection.

Returns: Style Dictionary JSON, `:root` CSS, Tailwind theme, Figma Variables
collection. This is the endpoint that answers *"drop it into Figma."*

### 4.3 `POST /api/v1/voice` — voice & messaging lab *(never shipped as a route)*

`{ url }` → linguistic analysis. Goes **deeper into copy** than the kit: crawls
content pages by intent (`/about`, `/careers`, `/blog/*`, `/press`, `/pricing`,
`/manifesto`), then runs sentence-level analysis — mean sentence length,
reading grade, you/we ratio, contraction rate, hedging, intensifiers, jargon
density, emoji/exclamation rate, formality, sentence-opener diversity.

Returns: tone vector, per-page consistency score, voice **do / don't** lists
populated with real sentences quoted from the site, boilerplate vs distinctive
copy split, message pillars with source URLs, tagline candidates.

### 4.4 `POST /api/v1/compare` — brand benchmark

`{ brand, competitors: [] }` → positioning report. `Search` finds each
competitor's official domain, then all brands go through the same identity +
voice pipeline. Diffs: CIEDE2000 colour distance, font overlap, cosine distance
between tone vectors, Jaccard overlap of message pillars, token-sharing.

Returns a whitespace analysis and a ranked "what is distinctive about this
brand" list. 2–5 brands.

### Supporting routes

> **As built.** `GET /api/v1/schema` was planned and does not exist; the schema is
> exported from `src/schema.js` as `BRAND_GUIDE_SCHEMA`. `GET /api/v1/health` was
> planned to report key presence and upstream reachability; it ships as liveness
> only and deliberately makes no upstream call, so a platform health check can
> point at it safely. `POST /api/v1/llm-check` and `GET /api/v1/stream` were added
> and are not in this list.

- `GET /api/v1/health` — liveness and the credential header names. No upstream call.
- `GET /api/v1` — the provider preset catalogue.
- `GET /api/v1/stream` — SSE, so the UI can show each source as it is read.
- `POST /api/v1/llm-check` — one minimal request against a narration credential.
- `GET /` — the UI.
- `?format=` on brand-guide and compare only: `json` · `markdown` · `css` ·
  `tailwind` · `styledictionary` · `figma` · `svg`.

## 5. Non-functional requirements

| Requirement | Target | Status |
| --- | --- | --- |
| Runtime dependencies | **0** | met |
| Cold start | < 100 ms | **unmeasured.** No test or benchmark asserts it. |
| Single guide, depth `standard` | < 45 s wall clock | **unmeasured.** The only per-run timing in code is per-call `durationMs` in the provenance block. The UI's own copy says "a 25-second crawl". |
| Works for any public site | no hardcoded domains, brands, or selectors | met |
| Every claim traceable | each extracted value carries `source` (URL + how) | met |
| Graceful degradation | per-URL fetch errors collected, never fatal | met |
| Secrets | env only, never logged, never returned | met, and stronger than planned: keys are per request in headers, so the server stores none at all |

The two timing figures were targets, not commitments, and nothing measures them.
Either add a benchmark or drop them; do not leave them looking like results.

### Constraints

- Fetch allows 10 URLs per call and ~150 URLs/min per key. The pipeline batches
  into as few calls as possible and runs stages concurrently.
- Fetch has a 120 s CDN ceiling per batch; client timeout set to 150 s.
- CSS files can be large. Cap at 2 MB per stylesheet (`MAX_BYTES_PER_SHEET` in
  `src/crawl/css.js`), and at 50 stylesheets at `standard` depth, 60 at `deep`
  (`src/pipeline/collect.js`). The planned cap of 12 was too low: Linear declares
  49 and the brand tokens live in the last one.
- Private IPs and localhost are rejected upstream — SSRF is handled by TinyFish.

## 6. Accuracy strategy

Criterion 2 is *extracted details are accurate to the live site*, so:

1. **Ground truth over inference.** If `<meta name="theme-color">` says `#08090a`, that is the background token. Not a guess from pixel sampling.
2. **Prefer declared intent.** `--color-bg-primary` outranks a raw `#08090a` found 40 times in a stylesheet.
3. **Verify, don't assume.** A logo URL is only returned if `Fetch` on it returns extractable content.
4. **Never let the LLM invent.** Interpretive output is a separate block that cannot overwrite extracted facts.
5. **Show the receipts.** The UI renders a provenance panel listing every TinyFish call with its latency. Reviewers can audit any number against the URL it came from.
6. **Confidence per section**, derived from how many independent sources agreed.

## 7. UI

Single page, no build step. The differentiator: **the guide renders as a paged
document set in the brand's own colours and typefaces**, loaded live from the
extraction. A marketer sees the guide, and sees it in the identity it documents.

The document is a fixed 1200x900 landscape canvas scaled to fit, so the same
page looks identical on a laptop and on a projector, and prints one landscape
sheet per page. Layout follows the conventions of a real guidelines document:
a two-column running header carrying the source domain, a rule, then content.

Sections, each opening on a full-bleed plate page:

| Section | Pages |
| --- | --- |
| Introduction | Contents, about the brand, positioning, message pillars, tone of voice, aim and vision (written) |
| Logo | Logomark, asset register, clear space |
| Color | Palette with RGB/CMYK and tint strips, contrast combinations, neutral ramp |
| Typography | Typeface, weights, type scaling, writing in this voice |
| Method | Sources read, confidence |

The UI ships two outputs: **Guide** and **Compare**. The deep Identity and
Voice endpoints remain fully available over the API but are not surfaced in the
UI, where the paged guide already carries the identity and tone measurements in
a form a marketer can use.

Composer (top of the stage): input, submit. Rail (left): output mode, compare
against, **guide length**, read depth, examples. Output: the deck with a
document header (name, domain, confidence, page and stylesheet counts), then the
export strip.

While a run is live, the sources read appear in a modal dialog that closes itself
when the pipeline does. A permanent panel of internal telemetry is not shipped
in the product; the same facts are one line in the document header, and the full
per-call provenance is in the response body.

### 7.1 Two output modes

The deck renders one of two documents, decided by whether a narration layer
produced content.

**Deterministic (no LLM key), the default: seven measured pages.**

Cover · Logomark · Logotype · Color palette · Typeface · Weights · Type scaling

Every one is a measurement: a verified asset URL, a resolved hex, an
`@font-face` declaration, a size the site actually uses. Nothing on them is
written, because a brand cannot be summarised from a hex value. The prose
describes the extraction, not the brand.

**LLM configured: the full document.** Cover, contents, and the sections that
need writing: about the brand, positioning, message pillars, tone, values,
application, sources and confidence. The LLM is structurally barred from colour,
type and logo values, so it can fill pages but never alter a measurement.

The page budget (`pages`, 4 to 24) applies to the full document. In
deterministic mode the control is disabled and explains why.

A page is emitted only if it can be filled truthfully. Nothing is padded to hit
a number, and a shortfall is stated on the page rather than hidden.

### 7.2 The brand name, and which logo

The cover carries the brand name at 76px, which makes it the single most
conspicuous value in the document. It is always the **fetched** name, resolved
from the site's own metadata (`og:site_name`, the web app manifest, the domain
as the site writes it, headings), never the URL that was pasted in. The name is
set in the brand's **own capitalisation**: `tailwindcss` is never rendered as
`TAILWIND CSS`, because the casing is part of the identity.

The best *mark* and the best *lockup* are usually different assets, so the
extractor returns both.

| | `logos.primary` | `logos.lockup` |
| --- | --- | --- |
| Chosen by | SVG first, then highest score | Declared aspect ratio 2.2 or wider, then a logo-ish filename, then the og:image |
| Usually | The app icon | The mark plus wordmark |
| Used on | The Logomark page | The Cover only |

This split exists because of Tailwind: the SVG in its head is a dark rounded
square, which outscores everything and is invisible on a dark plate. The real
logo is a wide asset in the page body. `lockup` is `null` when the two are the
same asset, so a consumer can tell "none found" apart from "same file".

### 7.3 The document is always light

The paper and the ink are fixed and never taken from the brand. A brand guide
that inherits a dark brand's background stops being a document and becomes a
screenshot of that brand's site, and a print of it comes out as a book of black
pages.

What the brand does change is the type it is set in, and the colour of every
swatch, plate and specimen drawn on the page.

### 7.4 Logos keep their colour

A logo loaded through `<img src="…svg">` cannot inherit anything from the page,
and a large share of real brand SVGs are built to inherit: `fill="currentColor"`
is how most design systems ship one file that works on light and dark. Loaded as
an image, `currentColor` resolves against the SVG's own default, so a cyan
Tailwind mark arrives flat black. That was the greyscale logo, and it was never a
filter or a bad asset, just an image boundary doing what images do.

So the extractor reads the SVG source through TinyFish Fetch and returns it as
`logos.primary.svg`, sanitised. The deck inlines that markup rather than pointing
an `<img>` at the URL, so `currentColor` resolves against the page and the real
colours come through.

Two consequences worth stating plainly:

- **Inlining remote markup is a script-injection risk, so it is stripped.**
  Scripts, event handlers, external `href`, external `url()` paint servers,
  DOCTYPE/ENTITY declarations and `javascript:` are all removed before the source
  leaves the server. The deck additionally parses with `DOMParser` and adopts
  nodes one at a time, never assigning to `innerHTML`.
- **The surface follows the asset, not the other way round.** `svgTone` reads the
  mark's own fills and gradient stops and reports `light`, `dark` or `inherit`. A
  white mark is shown on a dark plate and a dark mark on a light one, because a
  white mark on a white page is the same class of bug as the greyscale one.

The **Logotype** page deliberately does *not* show the lockup. A logotype is the
wordmark on its own, so that page sets the name in the brand's heading face
inside a bordered box, which is also what the reference deck does. The mark has
already been shown on the page before it.
